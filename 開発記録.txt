■ 2026-10-08 立ち上げ
- ビジネスダイアグラムメーカーから分かれて、別のリポジトリで作ることにした。理由は 引継書.md の 3 章。
- 引継書 9 章の 1〜5（ファイルを置く・.gitignore・Puppeteer・フック）を、クラウドのセッションで済ませた。
  - GitHub のリポジトリが空で main がなかったため、ユーザーの指示で、この準備のコミットだけは PR を通さずに main にも置いた。
  - フックの登録は、参考の手順の「絶対パス」でなく $CLAUDE_PROJECT_DIR で書いた。クラウドと共同開発者のデスクトップの両方で同じ設定を使うため。
  - フックの対象は Bash と PowerShell の両方にした（引継書 9 章の 5 の任意の項目）。止めるのは main への push だけなので、足しても困ることはない。
  - フックの文言から、ビジネスダイアグラムメーカーの記憶（memory）の名前を消した。このリポジトリにはない記憶のため。参考/ の写しは元のまま。
  - Puppeteer は、クラウドのセッションでは npm の取得が拒まれた（403）ため、package.json に書くだけにした。

■ 2026-10-08 共同開発者のデスクトップでの準備

  - npm 11 の allowScripts により、Puppeteer の postinstall（同梱 Chrome の取得）は走っていない。
    検証はシステムの Chrome（channel:'chrome'）で行うため、承認しないままでよい（引継書 7-3）。
  - 引継書 7-3 の起動設定で、headless の Chrome（154）が起動し、撮影できることを確かめた。

- core.autocrlf=true のため、作業フォルダのファイルは CRLF になる。参考/ の diagram_v8.31.html・serve.js・AI向け仕様書.md は、Git の中でも CRLF。
- コミットの名義は、このリポジトリの中だけ ashikagagassoumu-cmd と GitHub の非公開用アドレス（noreply）にした。
  公開リポジトリのため、会社のメールアドレスをコミットの記録に残さない（ユーザーの選択）。

■ 2026-10-08 引継書 4 章のまだ決まっていないことを決めた
見た目に関わる問いは、HTML のモックの画像（screenshots/q3〜q5・q11。Git には入れない）を見せて聞いた。
- 作る先: kintone は例に挙げただけ。kintone・Salesforce・Claude で作るアプリなど、いろいろな業務アプリの画面の見た目を伝えるために使う。
- 部品の名前: 一般的な名前にする。作る先が 1 つに決まっていないため（最初は保留。描く画面が決まった後に聞き直して決まった）。
- 描く画面: 入力・詳細、一覧、グラフ・集計、進み具合と操作ボタンの 4 種類すべて。
- 部品の置き方: マス目に合わせて置く（どこにでも置けて、位置と大きさはマス目に吸い付く）。
  行に左から詰める形は、グラフの画面のように行に並ばない画面に合わないため選ばなかった。
- 部品の設定の見せ方: 番号と一覧表に加えて、吹き出しも使える。一覧表は画面ごとに右か下かを選べる
  （入力の画面は幅が狭いので右、一覧の画面は幅が広いので下、が合うため）。
- 複数の画面: 画面ごとにページを切り替える（左に画面の一覧）。印刷・PNG は 1 画面ずつ。
- ベンダーへの渡し方: HTML ファイルと PDF。PNG は作れるようにするが、見栄えの調整は後にする。
- アプリ名: モックイメージメーカー（リポジトリ名 MockImageMaker をカタカナにしたもの）。
- 公開範囲: public のまま。社内の実際の画面・資料・実際の業務を描いたデータはコミットしない。
- 画面のつながりの図をどのアプリで描くか: 保留。
- 運用ルール（CLAUDE.md の「案」）: 版の上げ方を除いて、そのまま確定した。

■ 2026-10-08 デスクトップアプリ（Electron）にした
- 引継書の前提は「ブラウザで開く 1 つの HTML ファイル。保存すると、アプリ本体と図のデータが入った HTML ファイルになる」だった。
- 画面のつながりの図を聞いた問いへの答えとして、ユーザーから「モックイメージメーカーは独立したデスクトップアプリとして開発する」
  「GitHub の CheckListMaker を参考にする。あんなイメージでアプリにする」と示された。
  CheckListMaker（kuwagata-137/CheckListMaker）は、画面を 1 つの HTML で作り、Electron で包んでインストーラで配るアプリ。
  これと同じ形で作ることを、ユーザーに確かめて決めた。
- 保存のしかた: アプリの中に一覧で自動保存する（CheckListMaker と同じ）。ベンダーに渡すときに HTML・PDF に書き出す。
  Claude は「1 つの画面設計を 1 つのファイルに保存する（Excel と同じ）」を推したが、ユーザーはアプリの中への保存を選んだ。
- これにより、ビジネスダイアグラムメーカーの「ファイルへの上書き保存」の仕組み（File System Access API・上書き先の記録）は写さない。
  引継書 7-1 の保存の注意点の多くは、ベンダーがブラウザで HTML を開いて保存し直す場面にだけ関わる。
- PDF は Electron の printToPDF で作る。用紙の大きさと向きを直接指定できるため、引継書 7-2 の @page の問題（プリンターによって向きが縦に固定される）を避けられる見込み。
- 版番号: ファイル名に版を入れる形（mock_v1.00.html）のまま、作業 1 回ごとに 1 つ上げる。
  - Claude は CheckListMaker と同じ「ファイル名は index.html に固定し、版は package.json だけに持つ」を推した。
    Electron の起動設定とインストーラの設定に HTML のファイル名が書かれ、版のたびに直す手間があるため。
    ユーザーは、ファイル名に版を入れる形を選んだ。
  - インストーラ用の版番号（3 つの数字）との対応（v1.00＝1.0.0、v1.01＝1.0.1）は Claude が決めた。
  - 作業 1 回ごとに上げるのは、インストールしたアプリがどの時点のものかを版番号で見分けるため。
