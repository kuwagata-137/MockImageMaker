# 次の開発の引継を書く・読む（dev-handoff）

このスキルは、次のセッションが最初に読むファイル `次の開発の引継.md`（リポジトリの直下）の書き方と読み方を決める。
目的は、開発の計画を立てるたびに、設計書・ロードマップ・前のプラン・細かい決めごとを丸ごと読んでコンテキストを使い過ぎないようにすること
（2026-10-15 ユーザー決定。`CLAUDE.md` の「次の開発の引継（ルーティン）」）。
立ち上げのときの `引継書.md` とは別のファイル。`引継書.md` は直さない。

## 書く時

- セッションの終わり（PR を作る前の最後のタスク）。
- 段階の区切りで、次のセッションへ渡すとき（例: 第 9 段階の前半が済み、後半を次のセッションで作るとき）。
- 書き直したら、ほかの文書と同じくコミットして、そのセッションの PR に入れる。

## 型（この順の 7 つの見出し）

`次の開発の引継.md` は、次の 7 つの見出しをこの順に置く。書くことがない見出しも消さずに「なし」と書く。
いちばん上の行には、書いた日・ブランチ・書いた時点の最後のコミットを書く（読む側が、今の Git の状態と合うかを見るため）。

```markdown
# 次の開発の引継（2026-10-15 に書いた。ブランチ stage9a/systems・最後のコミット 1234abc）

## ① 次に作るもの
## ② もう決まっていること
## ③ ユーザーに聞くことの案
## ④ 触る関数とファイル
## ⑤ 前回分かった落とし穴
## ⑥ 確かめの道具とテストの数
## ⑦ 必要なときだけ読む資料
```

見出しごとに書くこと:

- ① 次に作るもの: 範囲（段階の番号と名前・前半か後半か・作るものの箇条書き）と、終わりの確かめ（何ができたら済んだとするか。
  テスト・確かめの道具・撮る場面・Claude Code から試す場面）。範囲の外に回すもの（次の次の段階で作るもの）も 1 行で書く。
- ② もう決まっていること: ユーザーの決定（日付つき）と、設計書の該当する節の要点と行番号
  （例: `AI設計基盤_設計書.md` の「5-3. システム」L192〜。2026-10-15 の時点の行番号）。決定は要点だけを書き、設計書の本文は写さない。
- ③ ユーザーに聞くことの案: 作る前に聞く問い（番号は前の問いの続き。例: q61〜）。問いごとに、選択肢と Claude の推す案とその理由。
  見た目に関わる問いは、モックの画像で聞く（グローバルの「UIモック提示ルール」「質問の書き方ルール」）。
- ④ 触る関数とファイル: 1 行に 1 つ、`ファイル:行 関数名 — 何に使うか（使い回す・直す・足す）` の形で書く。使い回せる今ある関数を先に書く。
- ⑤ 前回分かった落とし穴: 前のセッションでつまずいたこと・環境のくせ・見直しで見つかった不具合の型。次のセッションでも起こりうるものだけを書く。
- ⑥ 確かめの道具とテストの数: 今のテストの数（`npm test` の結果）と、使う確かめの道具（`tools/check-*.js`・`tools/shoot-app.js --only=…`）、書いた時点で通ったか。
- ⑦ 必要なときだけ読む資料: 設計書の節（番号・名前・行番号）・画像の名前（`screenshots/q*.png`）・`仕様_細かい決めごと.md` の節・`作りの地図.md` の節・
  `開発記録.txt` の見出し。資料ごとに「何のときに読むか」を添える。

## 字数と書き方

- 1.5 万字まで。字数は node で数える: `node -e "console.log([...require('fs').readFileSync('次の開発の引継.md','utf8')].length)"`
  （Git Bash の `wc -m` は、字ではなくバイトを数える。日本語は 1 字が 3 バイトなので、約 3 倍の数が出る。2026-10-15 に分かった）。
- 前のセッションの経緯（何をどの順にしたか）は書かない。経緯は `開発記録.txt` とコミットにある。
- 上書きしてよい。古い中身は Git の履歴にある。
- 行番号は書いた時点のもの。次のセッションではずれていることがあるので、関数名・節の名前を一緒に書く。
- 設計書から次の段階の節を抜き出す作業は、書く側の文脈を軽くするため、サブエージェント（Explore など）に任せてよい。
  任せるときは、抜き出す節の番号と、返してほしい形（要点と行番号）を指示する。
- 用語は `CLAUDE.md`・`仕様_細かい決めごと.md` と同じものを使う（言い換えない）。
- 実際の業務の画面・データは書かない（公開リポジトリ。`CLAUDE.md` の「運用」）。

## 読む側の手順（「開発の続き」と頼まれたとき）

1. `次の開発の引継.md` を読む（`CLAUDE.md` は自動で読み込まれている）。設計書・ロードマップ・前のプランは丸ごとは読まない。
2. ③の問いをユーザーに出し（見た目に関わる問いはモックの画像で）、答えをもとにプランを作る。
3. 足りないときだけ、⑦の資料の該当する節を読む。
4. 調べ役のエージェントは、④で足りない所（関数の場所・呼ばれ方）だけに使う。
5. `次の開発の引継.md` がないとき、またはいちばん上の行のブランチ・最後のコミットが今の Git の状態と合わないときは、
   `CLAUDE.md` の「開発を続ける前に確認するファイル」に戻って読む。

## 書いた後の点検

- 7 つの見出しがこの順にある。いちばん上の行に、書いた日・ブランチ・最後のコミットがある。
- ①に終わりの確かめがある。③の問いに Claude の推す案がある。④の行に関数名がある。
- 1.5 万字を超えていない。前のセッションの経緯を書いていない。
